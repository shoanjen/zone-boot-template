# zone-boot-template 派生接入手册（DDD 多模块模板）

> **版本**：v1.1（2026-11-28）· 适用模板基线：六模块 DDD（应用服务面向接口 + `service.impl` 子包 + 真实库示例链路）· zone-middleware-suite 1.0.0-SNAPSHOT（v1.66/v1.67 键面：db/redis 100% 官方键）
> **本手册回答一个问题**：如何用本模板派生一个**项目名、包名、端口、数据完全不同**的正式 Spring Boot 项目，同时完整继承它的 DDD 分层结构与开发规范。
> **边界**：zone-middleware-suite 二方包自身的模块选型、配置项、用法以 `zone-middleware-support/docs/接入手册.md` 为权威（785 行），本手册只固化模板已实测验证的接入姿势；工作区端口/环境/登记规范以总纲 `../AGENTS.md` 为权威。

## 1. 模板定位：带走什么、替换什么

| | 内容 |
|---|---|
| **随模板带走**（派生项目原样继承） | ① 六模块 DDD 分层结构与依赖方向；② ArchUnit 六条守护规则；③ 开发动线（domain → infrastructure → service → web）；④ 编码约定（fastjson2 禁 jackson、Lombok 优先、统一返回体、Controller 三件事、编程式事务、注入风格）；⑤ zone-middleware-suite 接入姿势（坐标落点、100% 官方键体系——db/redis 无 zone 键、type=pom）；⑥ 多环境 profile 骨架（dev/test/prod）与配置体系 |
| **派生必须替换**（禁止沿用） | ① 项目名 / Maven 坐标（groupId·artifactId·模块名）；② 包前缀 `com.zone.boot`；③ 主类 `ZoneBootApplication`；④ **端口 8212（总纲 4.3 第 6 条明令禁止沿用，必须按 4.2 双重检查申请新端口）**；⑤ MySQL 独立库名 `zone_boot_template`；⑥ Redis db index；⑦ 示例业务（订单查询/命令一条完整链路，30 个文件：29 Java + 1 Flyway 脚本） |

1. 已读总纲 `../AGENTS.md`：第一节流程 → 第二节环境 → 第三节共享服务 → 第四节端口规则 → 第五节总表 → 第九节开发规范。

## 3. 模板全景（派生前先看懂）

### 3.1 模块构成

| 模块 | DDD 角色 | 内容 | 关键依赖 |
|---|---|---|---|
| `zone-boot-common` | 通用层 | 工具类（Json/Ip/Base64/Map/Timestamp）、常量；**基础 starter 统一在此声明**（web/validation/actuator/aop/knife4j/springdoc/fastjson2），下游模块经传递获得 | lombok |
| `zone-boot-domain` | 领域层 | 充血实体、值对象、领域服务、领域事件、**仓储接口**、**防腐网关接口** | 仅 lombok（连 starter 都不传递进来） |
| `zone-boot-infrastructure` | 基础设施层 | DO（MP 注解只在此）、Mapper + XML、仓储实现、DO↔实体 Translator、外部网关实现（ZoneHttpTemplate） | zone-middleware-database、zone-middleware-http、domain、common |
| `zone-boot-service` | 应用层 | 应用服务接口（`service` 包）+ 实现（`service.impl` 子包，用例编排 + 事务边界）、领域服务装配（`config/DomainServiceConfig`）、通用业务组件（manager）、Req/Res DTO、Converter（领域对象→Res） | domain、common、zone-middleware-log、spring-tx（log 不带 tx，须显式声明） |
| `zone-boot-web` | 适配层 | Controller、Interceptor、WebConfig（CORS/拦截器预留）；全局异常处理与 Trace Filter 由二方包 `zone-middleware-web` 自动装配，模板不自有 | starter-web、aop、common、service、zone-middleware-log |
| `zone-boot-bootstrap` | 装配层（组合根） | 唯一启动入口 `ZoneBootApplication`、多环境配置、`@MapperScan`、打包可执行 Jar；**显式聚合 infrastructure 完成依赖倒置的运行期装配**；`DddLayerRulesTest` 守护测试 | web、service、infrastructure、**suite（type=pom）**、mysql-connector-j、archunit（test） |

### 3.2 依赖方向（单向，禁止回环/跨层）

```
            ┌─────────────┐
            │   common    │（任何层可用；不依赖任何业务层）
            └─────────────┘
 web ──────► service ──────► domain ◄────── infrastructure
（适配层）   （应用层）      （领域层）      （基础设施层：实现领域接口）
                                ▲
                bootstrap（装配层/组合根：运行期注入实现，测试域 ArchUnit 守护）
```

### 3.3 ArchUnit 六条守护规则（`zone-boot-bootstrap/src/test/.../arch/DddLayerRulesTest.java`）

| # | 规则 | 禁止 |
|---|---|---|
| 1 | 领域层框架无关 | domain 依赖 `org.springframework..` / `com.baomidou..` / `jakarta.servlet..` / `com.zone.middleware..` |
| 2 | 应用层不触基础设施 | service 依赖 `infrastructure..` / `com.baomidou..` / `com.zone.middleware.{http,redis,database}..` |
| 3 | 适配层不触基础设施 | web 依赖 `infrastructure..` / `com.baomidou..` |
| 4 | 基础设施不反向依赖 | infrastructure 依赖 `web..` / `service..` |
| 5 | 通用层中立 | common 依赖任何业务层 |
| 6 | 依赖方向总纲 | layeredArchitecture：适配层仅可被装配根访问；应用层仅被适配层访问；领域层被适配/应用/基础设施/装配根访问；基础设施层仅被装配根访问（运行期装配）；装配根（bootstrap）自由聚合各层且不被任何层访问 |

派生项目违反任何一条，`mvn test` 直接红。

### 3.4 完整包结构与各包职责（派生后按此对号入座）

> 关键分包均有 `package-info.java` 作为分包指南（该包放什么、红线是什么），新增代码前先读对应包说明；包前缀 `com.zone.boot` 派生时整体替换（见 Step 4）；拿不准放哪一层时，回查 5.1 职责表与 5.3 开发动线。

```text
zone-boot/                                  # 根 POM：聚合六模块 + dependencyManagement 统一钉版
├── zone-boot-common/                       # 通用层（无方向工具箱；基础 starter 统一声明处，供下游传递）
│   └── com.zone.boot.common
│       ├── constant/                       # 全局常量（ComStrConstant 等）
│       └── util/                           # 与业务无关的工具类（Json/Ip/Base64/Map/Timestamp）
├── zone-boot-domain/                       # 领域层（零框架依赖：禁 Spring/MyBatis-Plus/Servlet/zone.middleware）
│   └── com.zone.boot.domain
│       ├── entity/                         # 充血实体：业务规则写成实体方法、不变式守卫在构造器（Order）
│       ├── valueobject/                    # 值对象：不可变、按值判等（Money/OrderStatus）
│       ├── service/                        # 领域服务：跨实体/值对象的业务规则，纯 Java 由应用层 config 注册 Bean（OrderPricingService）
│       ├── event/                          # 领域事件：表达「已发生事实」的纯 record，由实体行为产出（OrderPaidEvent）
│       ├── repository/                     # 仓储接口：持久化契约，签名只出现领域对象（依赖倒置锚点）
│       └── gateway/                        # 防腐网关接口：外部系统的领域视角契约（UserGateway）
├── zone-boot-infrastructure/               # 基础设施层（技术实现；禁反向依赖 web/service）
│   ├── com.zone.boot.infrastructure
│   │   ├── persistence/
│   │   │   ├── dataobject/                 # DO：表映射对象，MyBatis-Plus 注解只允许出现在这里（OrderDO → t_order）
│   │   │   ├── mapper/                     # Mapper 接口（MP BaseMapper / 自定义方法；OrderMapper）
│   │   │   ├── translator/                 # DO↔领域实体翻译器（OrderTranslator；与应用层 converter 严格分工，互不代做）
│   │   │   └── repository/                 # 仓储实现：编排 Mapper+Translator 实现 domain 接口（OrderRepositoryImpl）
│   │   ├── gateway/                        # 防腐网关实现：出站统一 ZoneHttpTemplate，外部响应翻译为领域概念（MockUserGateway）
│   │   └── config/                         # 基础设施自身配置（预留）
│   └── src/main/resources/mapper/          # Mapper XML
├── zone-boot-service/                      # 应用层（用例编排；禁依赖 infrastructure 与 MyBatis-Plus）
│   └── com.zone.boot.service
│       ├── service/                        # 应用服务顶层接口：用例契约，Query/Command 读写分开（OrderQueryAppService / OrderCommandAppService）
│       │   └── impl/                       # 应用服务实现：编排用例 + 事务边界（编程式 TransactionTemplate，禁 @Transactional）
│       ├── config/                         # 应用层装配：领域服务等无法组件扫描 Bean 的 @Configuration 注册（DomainServiceConfig）
│       ├── manager/                        # 通用业务组件：编号生成/金额分摊/通用校验，只依赖 domain 与 common（OrderIdGenerator）
│       ├── converter/                      # 转换器：领域对象/事件 → 出参 Res（与 infra 的 translator 严格分工）
│       ├── request/                        # 入参契约 Req：校验注解在此，继承二方包 BaseRequest
│       └── response/                       # 出参契约 Res：应用服务组装返回，Controller 只包装不转换
├── zone-boot-web/                          # 适配层（HTTP 接入；禁依赖 infrastructure/MyBatis-Plus）
│   └── com.zone.boot.web
│       ├── controller/                     # REST 端点：三件事——接参数(@Valid)→调应用服务→ZoneResult.ok
│       └── config/                         # Web 配置：Interceptor/CORS 等协议层设施（WebConfig）
└── zone-boot-bootstrap/                    # 装配层（组合根；不写业务）
    ├── com.zone.boot.bootstrap
    │   └── ZoneBootApplication             # 唯一启动入口：scanBasePackages + @MapperScan
    ├── src/main/resources/db/migration/
    │   └── V1__create_t_order.sql          # 示例建表迁移（派生项目删除后放自己的脚本）
    ├── src/main/resources/
    │   ├── application.yml                 # 主配置（默认激活 dev；官方键 + zone 键，见第 9 节）
    │   └── application-{dev,test,prod}.yml # 三环境 profile
    └── src/test/java/…/arch/
        └── DddLayerRulesTest               # ArchUnit 六条守护测试（违规 mvn test 红）
```

## 4. 派生接入七步（按顺序执行）

> 以下以虚构项目 **`zone-order-center`（包前缀 `com.zone.ordercenter`，端口 8220）** 为示例演示改名动作；实际以你的项目为准。

### Step 1 复制模板

```bash
# 从模板仓库复制（或 git clone 后改目录名）；不要 fork 远端仓库
cp -R zone-boot-template/ zone-order-center/    # 复制后删除 .git、target、logs
```

新项目按总纲第八节走 `_templates/init_new_project.sh` 生成自己的 AGENTS.md 存根与工具别名（模板自带的 AGENTS.md 不带走）。

### Step 2 端口申请与登记（强制，先于一切启动）

1. 从 **8200–8299** 段取号（总纲 4.2），执行**双重检查**：
   - ① `lsof -nP -iTCP:<候选端口> -sTCP:LISTEN` 空闲；
   - ② 对照总纲第五节总表，未被其他子项目登记（含推荐端口汇总）。**8212 已被本模板登记，禁止沿用。**
2. 端口确定后**立即回填**：总纲第五节总表 + 本项目 AGENTS.md 存根速览 + 总纲第十节变更记录。不回填视为开发未完成。
3. 需要修改的位置（待 Step 4 改名后一并改）：`zone-boot-bootstrap/src/main/resources/application-dev.yml`（`server.port`）、主类 println 的 doc.html 地址、生产/测试 profile 如有端口声明。

### Step 3 Maven 坐标改名

| 位置 | 改什么 |
|---|---|
| 根 `pom.xml` | `groupId`（如 `com.zone.ordercenter`）、`artifactId`（如 `zone-order-center`）、`name`、`description`；`<modules>` 六个模块名同步 |
| 六个模块 `pom.xml` | `artifactId`、`<parent>` 引用、模块 `<name>`；相互依赖的 `groupId:artifactId` 全部指向新坐标 |
| `zone-boot-bootstrap/pom.xml` | `spring-boot-maven-plugin` 的 `<mainClass>` 指向新主类 |

模块重命名推荐保留「前缀-分层」结构（如 `zone-order-center-domain`），分层语义一目了然；`*-bootstrap` 这个名字建议保留（避让 DDD 应用层术语，见 README）。

### Step 4 包名迁移（`com.zone.boot` → 新前缀）

目录树与代码引用同步迁移，**触点清单如下（逐一核对，漏一处启动/测试即红）**：

| # | 触点 | 位置 |
|---|---|---|
| 1 | 六个模块的目录树 | `src/main/java/com/zone/boot/{common,domain,infrastructure,service,web,bootstrap}` → `src/main/java/com/zone/ordercenter/...`（含 `package-info.java` 的 package 声明；domain 还要移动 `src/main/resources` 下的 Mapper XML 如有） |
| 2 | 主类 | `ZoneBootApplication` 改名（如 `OrderCenterApplication`）；`@SpringBootApplication(scanBasePackages = "com.zone.ordercenter")`；`@MapperScan("com.zone.ordercenter.infrastructure.persistence.mapper")` |
| 3 | ArchUnit 守护测试 | `DddLayerRulesTest` 的 `importPackages("com.zone.ordercenter")` + 六条规则里全部包字面量（规则 6 的 layer 定义同改）；**类名与方法注释同步，规则与 README 分层节一一对应** |
| 4 | `application*.yml` 四份 | `spring.application.name`、`logging.level.com.zone.ordercenter`、`mybatis-plus.type-aliases-package`（若启用，指向新 infrastructure DO 包）、knife4j `title`/`description`、`logging.file.name`（如 `logs/zone-order-center.log`） |
| 5 | —（db/redis 已无 zone 键） | 二方包 v1.67 后 `zone.middleware.db.mybatis.*` 等键已删除；Mapper 扫描走主类 `@MapperScan`，无配置触点 |
| 6 | javadoc `@author` | 模板示例用 `ZoneBoot`，按项目实际署名替换 |

**残留自查（验收前必须零命中）**：

```bash
grep -rn "com\.zone\.boot\|zone-boot\|zone_boot\|ZoneBoot\|8212" \
  --include="*.java" --include="*.xml" --include="*.yml" --include="*.properties" \
  --exclude-dir=target --exclude-dir=.git .
```

### Step 5 数据隔离（共享实例，禁止另起实例）

1. **MySQL**：连接共享实例 3306，建**独立 database**（如 `zone_order_center`），禁止与任何已登记库名重名：
   ```bash
   mysql -uroot -prootroot -e "CREATE DATABASE IF NOT EXISTS zone_order_center DEFAULT CHARACTER SET utf8mb4"
   ```
   修改三份 profile 的 `spring.datasource.url` 库名。
2. **Redis**：连接共享实例 6379，取一个未被其他项目占用的 **db index**（对照总纲第五节总表各项目 Redis db：模板 dev 用 1、ai-mistake 3、llm-gateway 4/5、license 6/7……），改 `application-dev.yml` 的 `spring.data.redis.database`；测试/生产按需再分。
3. **Flyway**：模板已开启，启动自动执行 `classpath:db/migration`（内置示例建表 `V1__create_t_order.sql`）；派生项目删除示例迁移后放自己的脚本；存量库模板已默认 `baseline-on-migrate=true` + `baseline-version=0`（基线到 0 保证 V1 起跑）。

### Step 6 删除示例链路（回到纯骨架）

删除以下 **30 个文件**（29 个 Java + 1 个 Flyway 脚本；包内 `package-info.java` 保留不动）：

| domain（7） | `entity/Order`、`valueobject/Money`、`valueobject/OrderStatus`、`repository/OrderRepository`、`service/OrderPricingService`、`event/OrderPaidEvent`、`gateway/UserGateway` |
| service（15） | `service/OrderQueryAppService`、`service/OrderCommandAppService`、`service/impl/OrderQueryAppServiceImpl`、`service/impl/OrderCommandAppServiceImpl`、`config/DomainServiceConfig`、`manager/OrderIdGenerator`、`converter/OrderConverter`、`request/OrderListReq`、`request/OrderQueryReq`、`request/OrderCreateReq`、`request/PayOrderReq`、`response/OrderDetailRes`、`response/OrderSummaryRes`、`response/OrderCreateRes`、`response/PayOrderRes` |
| infrastructure（5） | `persistence/dataobject/OrderDO`、`persistence/mapper/OrderMapper`、`persistence/translator/OrderTranslator`、`persistence/repository/OrderRepositoryImpl`、`gateway/MockUserGateway` |
| web（2） | `controller/OrderController`、`controller/OrderCommandController` |

> 注：模板 README「删除两示例共 20 个文件」为笔误，以本清单 21 个为准。

### Step 7 验证

## 5. 分层规范（派生后日常必须遵守）

### 5.1 各层职责与红线（ArchUnit 守护）

| 层 | 放什么 | 红线 |
|---|---|---|
| domain | 充血实体（业务规则写成实体方法 + 构造器不变式守卫）、值对象（不可变 record/按值判等）、领域服务、领域事件、仓储接口、防腐网关接口 | **零框架依赖**：禁 Spring / MyBatis-Plus / Servlet / zone.middleware；实体禁持久化注解；方法签名只出现领域对象 |
| infrastructure | DO（MP 注解只在此）、Mapper + XML、仓储实现（`persistence.repository` 实现 domain 接口）、DO↔实体 Translator（`persistence.translator`）、外部网关实现（`gateway` 包，用 ZoneHttpTemplate 实现 domain.gateway 接口） | 不反向依赖 web / service |
| service | 应用服务接口（`service` 包）+ 实现（`service.impl` 子包，用例编排 + **事务边界**）、领域服务装配（`config/`）、通用业务组件（`manager` 包，只依赖 domain）、Req/Res DTO（`request`/`response`）、转换器（`converter`，实体/值对象 → Res）、领域事件发布（事务提交后） | 禁依赖 infrastructure 与 MyBatis-Plus；禁触 `zone.middleware.{http,redis,database}`（数据访问只经仓储接口，出站 HTTP/Redis 归 infra）；事务编程式 `TransactionTemplate` 禁 `@Transactional`；返回 Res 不返回 ZoneResult（包装归 web） |
| web | Controller、Interceptor、WebConfig；全局异常处理与 Trace Filter 交给二方包 `zone-middleware-web` 自动装配（模板不自有） | 禁依赖 infrastructure / MyBatis-Plus；Controller 只注入应用服务，三件事：接参数（@Valid）→ 调应用服务 → `ZoneResult.ok(res)`；不写业务、不做 DTO 转换 |
| bootstrap | 启动类、多环境配置、`@MapperScan`、显式聚合 infrastructure | 不写业务代码；它是唯一同时认识 web+service+infrastructure 的模块 |
| common | 工具类、常量；基础 starter 声明 | 不依赖任何业务层 |

### 5.2 依赖倒置与装配根（本模板的核心机制）

- 仓储/防腐**接口定义在 domain**（依赖倒置锚点），**实现在 infrastructure**，应用服务只依赖接口；
- **bootstrap 装配根显式聚合 infrastructure**，Spring 运行期把实现注入接口（`@Repository` 标注的实现类被组件扫描发现即可，无需手写装配 Bean）；
- **领域服务等不能用 `@Service` 声明的纯 Java 对象，由使用方所在模块的 `@Configuration` 注册**（应用层 `config/DomainServiceConfig` 示范；跨模块装配归装配根），应用层经构造器注入使用；
- 收益：domain 可单测不起容器、可整体替换持久化技术栈；service/web 对「数据从哪来、外部服务怎么调」完全无感。

### 5.3 新业务开发动线（照此填代码即合规）

1. **domain**：建实体（业务规则写成方法，不变式守卫写进构造器）→ 需要持久化时在 `repository` 定义接口；跨实体规则写**领域服务**（纯 Java，应用层 config 注册 Bean）、领域事件由实体行为产出、外部 API 在 `gateway` 定义防腐接口；
2. **infrastructure**：建 DO（表映射）+ Mapper + Translator（DO↔实体）→ `persistence.repository` 实现仓储接口；防腐网关在 `gateway` 包实现（出站走 ZoneHttpTemplate）；
3. **service**：定义应用服务**接口**（`service` 包）+ **实现**（`service.impl` 子包，注入仓储/网关接口编排用例；事务边界在实现，写路径用编程式 `TransactionTemplate.execute`，禁 `@Transactional`，只读链路不包事务）；读写职责分开（查询侧 Query 服务 / 写侧 Command 服务）；Req/Res 放 `request`/`response`、转换器放 `converter`、通用业务组件放 `manager`；
4. **web**：Controller 接 Req（@Valid 触发校验）→ 调应用服务 → `ZoneResult.ok(res)`。

### 5.4 对象模型分工（转换不跨层代做）

| 对象 | 所在层 | 说明 |
|---|---|---|
| entity / valueobject | domain | 领域模型，业务行为内聚 |
| DO（dataobject） | infrastructure | 表映射，MP 注解只在此 |
| Req / Res | service | 接口契约；Req 继承二方包 `BaseRequest`，校验注解在 Req |
| Converter | service | 领域对象 → Res（DTO→VO 归应用层） |
| Translator | infrastructure | DO ↔ 实体（与 Converter 严格分开，互不代做） |

### 6.3 读代码时的五个常见偏差对照

| 常见偏差 | 示例中的正确姿势 |
|---|---|
| Controller 里做转换/写业务 | Controller 永远三件事；转换在 `converter`（实体→Res）与 `translator`（DO↔实体）两处，职责严格分开 |
| 事务用注解随处标 | 接口只有契约；`@Transactional` 全工程禁用，写路径在 impl 用 `TransactionTemplate.execute` |
| DO 与领域实体混用 | DO 不出 infrastructure；实体不沾持久化注解；互转只经 Translator |
| 事件随事务一起发 | 事件在事务提交后发布 |
| 直接注入 Mapper 绕过仓储 | 应用层只注入 domain 仓储接口；Mapper 只被 infra 的仓储实现认识 |

## 7. 编码约定（模板强制）

1. **JSON 统一 fastjson2，禁 jackson**（总纲 9.1）：HTTP 报文转换器、Redis 序列化、工具类、日志埋点全部 fastjson2；业务代码不得新增 jackson 调用。
2. **Lombok 优先**：`@Data`/`@Slf4j`/`@Builder`/`@RequiredArgsConstructor` 生成样板，禁止手写 getter/setter/equals/hashCode。
3. **注入风格**：统一 `@RequiredArgsConstructor` + `private final` 字段（Lombok 构造器注入），模板全量示例即此风格；多实现用 `@Qualifier` 区分。
4. **统一返回体与业务异常**：`ZoneResult.ok(...)` / `ZoneResult.fail(...)`；业务错误抛 `ZoneBusinessException(BusinessError, "补充消息")`，错误码复用二方包 `BusinessError`/`SystemError`，自定义错误码遵循手册 §4.2 码段约定（内置 `BIZ-4001–4099` 段禁侵）。
5. **Req 继承 `BaseRequest`**：通用契约字段（分页、签名等）继承二方包基类，不重复定义。
6. **Controller 三件事**：接参数（含 @Valid 触发校验）、调应用服务、组返回；格式校验在入口，业务规则校验在 service（判据：换个协议调用还成立吗）。
7. **日志用 ZoneLog 门面**：`ZoneLog.info/warn/error("类名", "方法名", "消息 {}", 参数...)`；Trace 上下文绑定/清理由二方包 Trace Filter 自动完成，业务侧只管打日志。
8. **命名**：遵循 `zone-coding-standards` skill 命名五条（业务贴合、禁宽泛词、禁多义词、禁无脑缩写、名字匹配数据状态）；分层归属拿不准时按本手册第 5 节对号入座。
9. **事务编程式**：禁 `@Transactional`，写路径用 `TransactionTemplate.execute` 只包写库原子片段（对齐 skill Spring Boot 惯例三）；只读链路不包事务；事件/消息发布在事务提交之后。

### 8.1 坐标落点

| zone 构件 | 声明在 | 说明 |

| `zone-middleware-suite` | **bootstrap** | 全量套件坐标只落一处；**必须声明 `<type>pom</type>`**（suite 是 pom 聚合坐标，缺省按 jar 解析直接失败 `Could not find artifact ...:jar:...`——阻断级坑） |

| `zone-middleware-common` | 传递获得 | ZoneResult / 异常 / BaseRequest 随上述构件传递，无需显式声明 |

### 8.2 配置键体系（二方包 v1.66/v1.67 后：db/redis 100% 官方键）

- **连接/池/迁移/HTTP 超时一律 Spring Boot 官方键**：`spring.datasource.*`、`spring.data.redis.*`、`spring.flyway.*`、`spring.http.client.*`；布尔 `ssl` 键为对象键 `ssl.enabled`（缺省即关）；**`zone.middleware.{db,redis}.*` 已无任何键**（预设层拆除）。
- **redis 连接池需显式配置方启用**（`spring.data.redis.lettuce.pool.*`，commons-pool2 已随包引入，模板已按原 LOCAL 预设值显式声明）；TCP 保活无官方键，按需自声明定制器 Bean（二方包手册 §6.1 配方）。
- **zone 键仅剩**：`zone.middleware.log.*`、`zone.middleware.security.*`、`zone.middleware.http.max-concurrent-requests` + `retry.*`（并发/重试无官方对应）、`zone.middleware.web.*`；HTTP 超时/重定向迁官方 `spring.http.client.*`。

  middleware:
    web:
      exception-advice-enabled: true   # 全局异常处理器：ZoneBusinessException 原码透传 / 校验异常转 BIZ-4001 / 兜底 SYS-9999

## 11. 常见问题（FAQ）

**Q1：能不能沿用模板的 8212 端口？**
不能。总纲 4.3 第 6 条明令：派生正式项目必须按 4.2 申请独立端口并回填总表。8212 已登记在模板名下，双重检查第 ② 道即拦截。

**Q2：`mvn test` ArchUnit 红了怎么办？**
规则即规范：红 = 违反第 3/5 节某条红线。常见两类：service 里直接注入了 Mapper/ZoneHttpTemplate（应改经仓储接口 / 下沉 infrastructure），Controller 里做了 DTO 转换（应移入 Converter）。改代码对齐规范，而不是改规则；确需调整规则时，同步更新项目 README 分层节与本手册依赖方向图。

**Q3：suite 引入报 `Could not find artifact com.zone.middleware:zone-middleware-suite:jar:...`？**
缺 `<type>pom</type>`。suite 是 pom 聚合坐标，必须显式声明 type（见 7.1）。

**Q4：启动报 sign secret 相关错误？**
suite 含 security 模块，`zone.middleware.security.sign.enabled` 缺省为 true 的场景会强制要求 secret。模板显式配置 `enabled: false`；启用签名则必配 `zone.middleware.security.sign.secret`（手册 §9）。

**Q5：示例仓储是什么形态？**
订单链路为**真实库全量示范**（`OrderDO` + `OrderMapper` + `OrderTranslator` + `OrderRepositoryImpl`，Flyway `V1__create_t_order.sql` 建表）——派生项目照此四件套模式接入自己的表，删除示例时连同迁移脚本一并删除；`@MapperScan` 已在主类指向 mapper 包。若某业务暂不需要落库（纯内存/外部 API），自建 mock 实现仓储接口即可——接口不变，service/web 零改动。

**Q6：为什么 service 模块要显式声明 spring-tx？**
`@Transactional` 注解来自 spring-tx，而 zone-middleware-log 不传递它（二方包手册 §2），service 又不依赖带 tx 的 starter，故显式声明 `org.springframework:spring-tx`。

**Q7：想要 Druid 监控页 / wall 防火墙？**
`spring.datasource.type` 指定 Druid FQCN + `spring.datasource.druid.filters=stat,wall`（别名未注册会启动快速失败）；监控页 StatViewServlet 由项目自行注册 Bean，参考二方包手册 §7.3。
